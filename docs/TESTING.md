# How Galleon is tested

Nobody tests by hand during development. CI proves the code on every pull request and every night; the **device bridge** on the Nova proves it on real hardware whenever the Nova is idle on its charger ([ADR 0004](decisions/0004-device-tests-any-hour.md)); the owner joins **once**, near the end, for an acceptance session of at most two hours ([ADR 0003](decisions/0003-autonomous-verification.md)). The tiers are listed in [PLAN.md section 3](PLAN.md#3-how-work-is-proven), the bridge's contract in [PLAN.md section 5](PLAN.md#5-the-device-bridge-hardware-in-the-loop), and the bridge program in [tools/device-bridge/README.md](../tools/device-bridge/README.md).

This file has one short part for the owner and the reference the agent works from.

---

## For the owner

**One habit, when it suits you.** Leave the Nova **on its charger, in Game Mode, at Steam's library** whenever you are not using it (quit any game, RomMix or ES-DE first), and set Steam's **Settings -> Power -> Sleep when plugged in** to **Never** once. Results then show up by themselves. If the Nova is away or asleep for days, nothing breaks; the features that need it simply wait.

**What you may notice.** At any hour while the Nova sits idle on its charger, the screen may show Galleon and a few emulators for up to about half an hour, with the sound muted. **Press any button** and the test stops at once and hands the Nova back. Your Steam library gains an entry called **Galleon Device Test**; starting it yourself does nothing. Nothing in your own RomMix, saves, emulator settings or RomM server is changed, and every run checks that.

**If something goes wrong once you use Galleon,** open Settings -> System -> **Report a problem**. The report reaches the developer automatically the next time the Nova is idle on its charger. There is nothing to file anywhere.

**Near the end** you get one GitHub notification e-mail: _Galleon is ready for your acceptance session_. Open the Claude session on your Mac and say **"start the Galleon acceptance session"**. It walks you through everything and does every terminal and GitHub step for you.

**Getting unstuck** (once Galleon is installed for you):

- **A game will not let go:** hold **Start** for about 1.5 seconds. If nothing happens after 10 seconds, press the Steam button and choose _Exit game_.
- **After turning on _Start on boot_, something is wrong:** hold **Select** while the Armada splash shows at power-on to land in Desktop Mode, then turn the option off there.
- **A graphics experiment left a black screen:** hold **B** while Galleon starts, to reset the graphics mode.

## Verification types

Every feature in [features.json](features.json) has exactly one:

| Type               | `passes` flips when                                                                                                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci`               | Its acceptance lines are proven by CI and the evaluator says PASS.                                                                                                                                                     |
| `agent-screenshot` | As `ci`, plus the agent and the evaluator have read the 1280x960 screenshots.                                                                                                                                          |
| `device`           | One device result, for a build that contains the feature, shows **every** `Device check` id in its acceptance as `pass`, with `safety.owner-state` and `safety.server-readonly` passing in the same run (rules below). |
| `acceptance`       | The owner marked its item pass in the acceptance session (`acceptance/<date>/results.json`).                                                                                                                           |

Acceptance lines use fixed prefixes the tooling reads:

- ``Device check `<id>`: <pass condition>`` (case-insensitive) names a check from the catalogue below. Only lines in `device` features gate `passes`.
- `On the device (informational): ...` and `Acceptance session (informational): ...` describe extra evidence; they gate nothing. The acceptance generator (M0-15) includes the informational acceptance lines in the session script.
- `Acceptance session: ...` is a plain-words step for the owner, in an `acceptance` feature.

## How a device feature passes

1. The feature's code merges with `READY-FOR-DEVICE <id>` in that PR's PROGRESS.md entry.
2. The next `nightly` pre-release carries it (one is published after every merge to `main` as well as on the nightly schedule, M0-24); the bridge tests it and publishes `results/<sha>/summary.json` on `device-results`.
3. At the next session start, `node scripts/agent/device-results.mjs --summary` shows the result. With `--apply` it flips `passes` when, in one summary:
   - every `Device check` id of the feature has `result: "pass"`, as the agent counts it: a check whose files the bridge must publish whole (`PUBLISHED_WHOLE` in `scripts/agent/features-check.mjs`, today `report.bundle`) counts as `fail` when `bridge.json`'s `sanitizer.withheld` or `sanitizer.dropped` names a file in its folder, and as `skip` when no `bridge.json` says what the sanitiser kept;
   - `safety.owner-state` and `safety.server-readonly` pass;
   - the summary's `status` is `complete` or `partial` (never `error`, `skipped`, `withheld` or `aborted-by-user`);
   - the commit that added `READY-FOR-DEVICE <id>` to PROGRESS.md is an ancestor of the tested sha.
4. The PR carrying the flip has `PASSES <id> device:<sha>` in its PROGRESS entry; features-check verifies all of the above against `origin/device-results` (M0-03).
5. If a later build fails one of the feature's checks, `passes` goes back to false and a `regression` issue opens. A failed safety check is a `regression` + `save-sync` emergency: feature work stops until it is understood.

A check that cannot run (no BIOS, no payload for a system, no importable sign-in, Steam's debugger unreachable) reports `skip` with a reason. A skip never counts as a pass.

## Check catalogue

Ids are lowercase, dot-separated; `@<profile>` marks a measurement repeated per power profile. The self-test (M0-21) runs the app-side checks; `run.sh` (M0-22) adds the harness checks. Thresholds live in `test/device/thresholds.json` and must match features.json and PLAN.md section 9.

`safety.owner-state` compares two manifests from `test/device/ownerstate.py`, one taken before the run starts anything and one after it stops, before any restore. What they cover (owner's RomMix and Galleon config and saves, following their root pointers; every emulator folder in DEVICE-FACTS.md; Steam's `shortcuts.vdf` files) is data in `test/device/owner-state.json`, as is the list of emulator config files backed up first and put back when changed. Links are recorded, never followed or written through, except that a covered folder which is itself a link (moved to the SD card, say) is read through it. A restore that put anything back fails the check as well. One difference is left out on purpose: Steam rewrites the 'Galleon Device Test' shortcut's `LastPlayTime` whenever it starts, and saves `shortcuts.vdf` when it likes, so for the shortcut lists named in `shortcutLists` the manifest drops the modification time and hashes the file with those four bytes zeroed (`shortcuts.play_time_spans`). Every other byte still counts, the owner's shortcuts and the test shortcut's other fields included, and a file that cannot be read as binary VDF, or is a link, is compared strictly. run.sh takes the first manifest and the config backup right after its session checks, keeps both in `$GALLEON_TEST_DIR/owner-state/` (never in `RESULTS_DIR`), and publishes only the comparison and the restore list as `logs/owner-state.txt`. When a manifest cannot be taken at all, `safety.owner-state` is `skip` and `harness.run` fails; `ownerstate.py` exits 1 only for a difference, so a crash is never read as one. A change is a `fail` whatever the restore did after it, and a restore that cannot finish is a `fail` of its own. The backup is deleted once its restore has run, and `run.sh --cleanup` restores from the backup a stopped run left (exit 1 when it cannot).

The app under test gets its own home from `test/device/signin.py`, recreated empty each run (never through a link). Its sign-in is imported read-only, first found wins: the bridge's `pair-readonly` token, the owner's Galleon, stock RomMix (each through its root pointer, and `ROMMIX_HOME`). Only a plain-text (`RAW1`) store is read; only its client or access token travels, never the refresh token or the device id. The test home's settings turn save sync off both ways and leave the device id empty; play sessions and every other write are stopped by the self-test's server guard. With nothing importable the home is still made and the server checks skip with `no-importable-credentials`.

`test/device/payloads.py` puts the bundle's homebrew payloads (`payloads/`, built from the M0-07 manifest) into the test home's ROM folder, the app's own, in their `roms/<system>/<file>` layout, so a payload's folder names its system. `copy` takes only entries of that shape, checks each file against its pinned size and hash, never reads or writes through a link, and never replaces a file already there; the licence notices stay in the bundle beside the payloads. A bundle without `payloads/` copies nothing, and the run asks for no emulator check. `remove` takes the whole ROM folder, payload copies and anything the app downloaded alike, never following a link out of the test home. run.sh copies them once the home is made; a copy that fails fails `harness.run`, and then no payload is named. It names RetroArch the GBA payload (`retroarch` in `payloads`, with `launch.retroarch` and `exit.retroarch`), ARMSX2 the PS2 disc (`armsx2`, with `launch.armsx2` and `exit.armsx2`), Dolphin the GameCube `.dol` (`dolphin`, with `launch.dolphin` and `exit.dolphin`), PPSSPP the PSP `EBOOT.PBP` (`ppsspp`, with `launch.ppsspp` and `exit.ppsspp`) and Flycast the Dreamcast `.elf` (`flycast`, with `launch.flycast` and `exit.flycast`), none with a save expected. While Dolphin, PPSSPP and Flycast are armadaOS's flatpaks, each one's checks skip as `cannot-sandbox`. Once the app has quit, run.sh removes the ROM folder, and `harness.run` fails when it is still there; `run.sh --cleanup` removes one a stopped run left.

`test/device/audio.py` mutes the default audio sink before a run starts anything and puts it back afterwards: `mute` records the sink by its id with its volume and mute (in a private file, kept if one is already there, since a stopped run's record holds the owner's settings and the sink may still carry that run's mute) and then mutes it; `restore` sets that same sink's volume and mute back and removes the record, which stays for `run.sh --cleanup` when the restore fails. WirePlumber that cannot be asked, or answers unexpectedly, exits 3, so run.sh can refuse to start anything with the sound on. `restore` sets the volume only when it differs from the record, since `get-volume` rounds. run.sh mutes once the launch request is written, keeping the record in `$GALLEON_TEST_ROOT/audio.json` so `run.sh --cleanup` finds it whichever build left it, and restores before the second owner-state manifest; the summary notes `audio: muted and put back`, `not muted` or `muted, not put back`. A failed restore fails `harness.run` and keeps the record, so a sink that has gone is reported on every run until it can be put back. A failed mute starts nothing and fails `harness.run`.

`test/device/powerprofile.py` switches Armada's power profile only when the app asks, and puts the owner's back. `record` reads the profile in force (`armada-power profile`, its label matched to a name through the profile definitions, `/etc` over `/usr/share`) into a private file, kept if one is already there for the same reason as the audio record. `answer` serves one request in the handshake folder (below, "Profile handshake"): a name the run measures is switched to with `armada-power profile <name>` and answered with the name once `armada-power` names it and policy7's governor matches the definition's `cpu_governor` (within `SETTLE_SECONDS`); anything else, a request that is linked, too large or not a name, a switch that does not settle, or a run with no record, is answered `unchanged:<current>` and switches nothing. It answers only while no answer is waiting, and never writes through a link. `restore` switches back to the recorded profile when another is in force and removes the record; one it cannot put back exits 3 and keeps the record. run.sh records once the sound is muted (`$GALLEON_TEST_ROOT/profile.json`; a run without a record notes `power profile: not recorded, so not switched`), serves requests for as long as it waits on the app, and restores just before the sound; a failed restore fails `harness.run` and `run.sh --cleanup` tries again.

`test/device/shortcuts.py` finds the 'Galleon Device Test' shortcut by name in each user's `shortcuts.vdf` (binary VDF, read only, never written) when run.sh's own record of its appid is gone, and turns the appid, stored signed, into the game id `steam://rungameid/` takes.

`test/device/steamcef.py` adds that shortcut while Steam runs, the way Armada Store does: `SteamClient.Apps.AddShortcut` evaluated in Steam's shared JavaScript context through its CEF debugger (loopback only), with Armada's game launcher as launch options when the device has it, and the name and launch options set again once the appid is back. The appid is kept in `$GALLEON_TEST_ROOT/shortcut.json`; a record is reused unless Steam has saved `shortcuts.vdf` since and left its appid out (the owner removed the shortcut). Without a usable record the shortcut is looked up by name before another is added. The same client starts a shortcut with `SteamClient.Apps.RunGame`, run.sh's fallback for `steam://rungameid/`. `ready` only reads the page list, asking again on a new connection until its wait ends, to learn that the client answers at all. A debugger that does not answer exits 10 with `steam-cef-unavailable` and a `detail` saying how it failed. With `--saved-within`, `ensure` also waits for the shortcut to be listed in a `shortcuts.vdf` under its name (and, when this run added it, with its launch options) and otherwise exits 10 with `steam-shortcut-unsaved`.

The shortcut's executable is `launch.sh`, copied with `current.py` into `$GALLEON_TEST_ROOT` so its path never changes. `steam://rungameid/` passes no arguments, so it starts what `$GALLEON_TEST_ROOT/current.json` names (run.sh writes it, private, just before the start and removes it after): the AppImage, with `GALLEON_HOME` set to a home inside the test root. A missing, linked, expired or unsound request starts nothing, which is what starting the shortcut by hand does. It marks the start in `$GALLEON_HOME/launch/` (`started`, `launch.pid`, `app.pid`, `app.log`, then `exit`), starts the app once however many routes reach it, and passes a stop it receives on to the app only. Before each pid file it writes, through `launched.py` (copied beside it), the boot id and the process's start time from `/proc` (`launch.id`, `app.id`). Past its start mark launch.sh execs `launched.py run`, which keeps its pid and start time, starts the app, passes the stop on and writes `exit` with the app's own status (128 plus the signal for an app a signal ended): a shell's `wait` interrupted by that stop can lose the app's status and give the stop's own. Steam starts the app outside the process group the bridge stops when run.sh overruns, so `run.sh --cleanup` runs `launched.py stop` before the sound is put back: SIGTERM to the recorded app and launch.sh, then SIGKILL, each only while its boot id and start time still match, so a pid reused after a reboot or after the app has gone is never signalled, and a pid without its record is left alone. Cleanup exits 1 when a recorded process is still running after both. `run.sh` and `launch.sh` are checked with shellcheck in CI.

Before anything else, run.sh takes the desktop session's variables (`DISPLAY`, `XAUTHORITY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `GAMESCOPE_WAYLAND_DISPLAY`) from `systemctl --user show-environment`, filling gaps from this user's exact-named `steam` process, and repeats the bridge's Game Mode and idle checks (imported from the bundle's `bridge/`, so the rules are the same) and a smaller free-space check (`session.py`). A failed check ends the run with exit 10 and a `skipped` summary giving the reason; a check that cannot run at all fails `harness.run`.

Next, run.sh copies `launch.sh`, `current.py` and `launched.py` into `$GALLEON_TEST_ROOT` (renamed into place, so a link there is replaced, never written through) and runs `steamcef.py ensure --saved-within`, all before the first owner-state manifest: the shortcut is the one change the run makes to `shortcuts.vdf` on purpose, and Steam saves that file when it likes, so the manifest is taken only once Steam lists the shortcut. `steam-cef-unavailable` and `steam-shortcut-unsaved` end the run with exit 10 and that reason (the next run finds the shortcut by its record or by name); any other failure there fails `harness.run`. After the manifest, `signin.py prepare` makes `$GALLEON_TEST_DIR/home`, exported as `GALLEON_HOME`, with the read-only sign-in import; with nothing importable the run goes on, and the summary's notes name the source kind (`sign-in: rommix`, say) or `sign-in: no-importable-credentials`. A test home that cannot be made fails `harness.run`. run.sh then writes the launch request `current.json` for this build and the test home, expiring when the bridge's budget (`DEVICE_TEST_BUDGET_SECONDS`, counted from run.sh's start) ends, and removes it once the run's work is done, before the summary; `run.sh --cleanup` removes one a stopped run left. A request that cannot be written or removed fails `harness.run`.

`test/device/selftestrequest.py` writes it (privately, renamed into place, never through a link, and only into a test home that is a real folder) and refuses what the app would refuse (a short sha, a version that is not plain, a budget that is not positive, a results folder that is not absolute), and beyond that a handshake folder that is not absolute, no checks, a saving payload with no payload, or a deadline that is not positive, none of which a sound harness writes. It writes `--deadline` (seconds since the epoch) as a UTC time. It always asks for the read-only server, privacy and the abort on input. `remove` takes the request and the app's taken copy, from a home that is a real folder only. It asks for the checks the app has scenarios for that need no payload, both power profiles and the three screenshots, and the emulator checks of each payload copied (`payloads.py`, above). A request that cannot be written fails `harness.run` and no launch request is written; run.sh removes both requests before its summary, and `run.sh --cleanup` removes one a stopped run left.

run.sh then starts the app (PLAN.md section 5.3, steps 8 and 9), only for this build, only with both requests written and only once the sound is muted; a mute that fails starts nothing and fails `harness.run`. Just before the start it repeats `session.py check`: when the owner has taken the device back since the first one, nothing is started, everything set up is undone as after any run, and the summary is `skipped` with the reason (exit 10), still carrying `harness.run` and `safety.owner-state`. Since the bridge publishes a skip only once per build and reason, such a run whose checks did not all pass is `partial` instead (exit 0), with a note giving the reason, so its failures always reach the results; a check that cannot run fails `harness.run`. It then runs `steamcef.py ready` for up to `READY_WAIT_SECONDS`: both routes go through Steam's client, and a shortcut reused from its record asked it nothing, so a debugger that does not answer is skipped the same way, with reason `steam-cef-unavailable` and the detail in the log, instead of failing with "neither route started the app". It runs `steam steam://rungameid/<gameid>` (held to `START_WAIT_SECONDS`) and waits that long for launch.sh's `started` mark, then asks the debugger's `SteamClient.Apps.RunGame` (`steamcef.py run`) and waits again; when neither marks a start, `harness.run` fails with "neither route started the app". It then waits for the app to quit (launch.sh's `exit`, or its recorded `launch.pid` gone) until `STOP_RESERVE_SECONDS` before the bridge's budget ends plus one `STOP_WAIT_SECONDS`; past that it writes `stop` into the handshake folder, waits, sends SIGTERM to the recorded `launch.pid` (which passes it to the app alone), waits, and last sends SIGKILL to the recorded `app.pid` and `launch.pid`. It signals no other process. Before the sound is put back it withdraws `current.json` and makes launch.sh's start folder itself, so a start Steam acts on late finds nothing to start; when that folder is already there though no start was marked in time, the late start is stopped the same way at once (`app: started late, ...`). The summary's notes say `app: not started`, `exited <code>`, `stopped when asked`, `stopped by a signal` or `killed`; an app stopped at the end of its budget makes the run `partial`. Once the app has quit or been stopped, `test/device/mergesummary.py` merges the summary the app wrote in `RESULTS_DIR/app/` into `RESULTS_DIR/summary.json` (step 10). The harness's checks, version and times stand; the app's checks follow, each held to the schema below, with evidence paths moved under `app/` and none reaching outside it; its `device`, `power` and `safety` are taken; its notes are kept, prefixed `app:`, after `app summary: <status> (<reason>)`. An app summary that is missing, linked, too large, not JSON or for another commit is left out, and so is a check that breaks the schema or repeats a harness check's id; either makes the run `partial` with a note, never `complete`. An app status other than `complete` makes the run `partial`, except `aborted-by-user`: the run is then `aborted-by-user` and run.sh exits 20, unless a harness check did not pass, when it is `partial` with a note, since the bridge does not publish an aborted run and the failure would be lost. A merge that cannot run leaves the harness's summary, `partial`. An app started only late, after the run gave up on it, is not merged. While it waits on the app, run.sh serves the app's profile requests (`powerprofile.py answer`, above). Once the app has run (a late start included), run.sh hands the device back at Steam's library (step 11), since a game that quits leaves Steam on its page: `steamcef.py library` reads the route Steam's Game Mode window shows from the debugger's window list (the window titled `Steam Big Picture Mode` or `SP`, else the windows of `steamloopback.host` when they all show one route; the address under `/routes`), which changes nothing in Steam. Any `/library` screen but a game's page (`/library/app/...`) counts. When Steam is elsewhere, run.sh runs `steam steam://open/games` and waits up to `LIBRARY_WAIT_SECONDS` for the library, asking again on a new connection when the debugger leaves a request unanswered and never letting one request run past the wait (`steamcef.ANSWER_SECONDS` aside); when it does not come, or the window cannot be read, `harness.run` fails with "Steam was not left at its library" and the log names the route (whole within `/library`, else only its first part), or the first two parts of the paths Steam's own windows (host `steamloopback.host`) show. Nothing else from the debugger's list reaches the log: it also holds web pages, whose titles and addresses can name the account.

Before the first key the page is timed at rest for `IDLE_MS` from the first frame it draws after the highlight lands (a page that draws none before the probe's `GRID_TIMEOUT_MS` deadline, counted from its start, is a failed scroll, `no-frames`), reported but never judged, so a page held back by how its frames are paced is told apart from one held back by what a move costs. - Emulator sandbox (for every `launch.*` and `saves.*` check): an emulator starts only through `planSandbox`, in `$GALLEON_HOME/sandbox/<emulator>/` with `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` pointed inside it plus its descriptor's `sandbox` recipe (arguments after the program, environment, variables removed from the inherited environment, config files written into the sandbox), and it starts in the sandbox's root, so nothing it reads or writes relative to its working folder is the owner's (Eden and shadPS4 each take a `user` folder there as their whole portable layout, Dolphin is given its user folder below the sandbox's `XDG_DATA_HOME` with `-u`, which outranks its portable marker, PPSSPP keeps its whole memory stick under the sandbox's `XDG_CONFIG_HOME`, and Flycast is given an `emu.cfg` of the sandbox's own, which outranks any in the system config folders, with `XDG_DATA_DIRS`, `XDG_CONFIG_DIRS` and `FLYCAST_BIOS_PATH` removed, since a VMU it finds in a folder they name is moved into the sandbox and the original deleted). The owner's BIOS files reach `bios/`, or the sandbox folder the recipe names for an emulator that reads them from a fixed place (Eden's `data/eden/keys`, Flycast's `data/flycast`), as clones that share their blocks, or as plain copies where the filesystem cannot clone, never as symlinks: emulators write NVRAM and flash beside their BIOS. Copies past `BIOS_COPY_BUDGET` skip the check as `cannot-sandbox` (`bios-too-large`). An emulator whose recipe says it needs a BIOS dump to start (`needsBios`: ARMSX2, DuckStation) is skipped as `missing-bios` when its sandbox BIOS folder holds no file of its own after the copy (links do not count), so a Nova without the dump never fails the check on the emulator's own complaint. An emulator without a recipe, a recipe that declines the system, a flatpak or `scripts` install, an install whose path cannot be read with its links followed, a file of the owner's the recipe needs (RetroArch's core, Eden's `prod.keys`) that cannot be read, or a recipe file or BIOS folder outside the sandbox is never started: its check is `skip` with reason `cannot-sandbox`. A folder the emulator makes outside the sandbox whatever it is told (a recipe's `strays`, such as RetroArch's `/tmp/retroarch-tmp`) is removed after the run if it was not there before and is still empty. See `src/main/selftestsandbox.ts`.
- `launch.<emulator>` and `exit.<emulator>` come from one cycle per emulator: the sandbox is prepared, the emulator is started as the leader of a new process group, and the window list is polled for a window of any process in that group until one is focused or `WINDOW_TIMEOUT_MS` passes. A focused window is left up for `SETTLE_MS`, then the group gets SIGTERM and has `EXIT_GRACE_MS` to empty; past it the group is killed. The group is done when nothing of it is left running (a zombie, killed but not yet reaped, does not count), not when its leader exits: a leader that exits by itself leaves the rest of its group to the same SIGTERM, grace and kill. `launch` fails `no-window`, `not-focused`, `not-fullscreen` (only when the window list can tell) or `exited-early`; `exit` fails `killed`, `exit-code` (anything but code 0, dying on the signal included), `exited-early`, `not-refocused` or `save-unchanged`: once a launch that saw its window has its group stopped without a kill, Galleon's own window (one whose `_NET_WM_PID` is in Galleon's process group) must hold the focus within `REFOCUS_MS`, and a window list that cannot tell counts as not yet. For an emulator the request lists in `savingPayloads` (its payload writes a save while it runs), the sandbox's `saves` folder must differ after the stop from what it held before the start: a file added, removed, resized or rewritten (a new folder alone is not), links listed and not followed; an emulator not listed is never failed over it, and its change is still recorded. Whatever happens after the start, the group is asked to stop and, past the grace, killed before the next check (one that outlives even the kill is left to the owner-state manifest after a further grace) and the recipe's strays are cleared. A plan or preparation that cannot sandbox skips both as `cannot-sandbox`; a sandbox that throws while prepared is `error` / `prepare-failed` and a start that throws `error` / `spawn-failed`; an abort stops the emulator and skips both. Metrics: `windowMs`, `focused`, `fullscreen`, `biosFiles`; `exitMs`, `code`, `signal`, `killed`, `straysRemoved`, `refocusMs`, `saveChanged`. See `src/main/selftestlaunch.ts`. The window list is read over X11 from the session's display: a window is the group's when its `_NET_WM_PID` is in the group (`/proc/<pid>/stat`), looked for in `_NET_CLIENT_LIST`, else the root's children and their children; it is focused when it is (or holds) the window gamescope's `GAMESCOPE_FOCUSED_WINDOW` names, else `_NET_ACTIVE_WINDOW`, else the keyboard focus; and fullscreen is known only from its `_NET_WM_STATE`. See `src/main/selftestwindows.ts` and `src/main/x11.ts`.
- Which emulator and payload: each `launch.<emulator>` or `exit.<emulator>` the request names runs the cycle for the probe's installed `<emulator>` with `payloads[<emulator>]`, a path relative to `$GALLEON_HOME` (or absolute inside it) whose folder names the ES-DE system (`payloads/snes/hello.sfc` is `snes`). Both ids of an emulator share one cycle, run when the first of them is reached. Both are `skip` with `no-payload` when the request gives none, `payload-outside-home` when it resolves outside the test home, by its name or where its links lead (an emulator is never handed a file of the owner's), `payload-missing` when it is not on disk, and `not-installed` when the probe has no usable install of that emulator. `savingPayloads`, when given, is a list of emulator ids (a value that is not a list of strings refuses the request as `request-saving-payloads`). See `src/main/selftestemulators.ts`.

## The acceptance session

**When.** Every `ci` and `device` feature of M0-M7 passes (or is deferred by an ADR), and every `acceptance` feature is READY-FOR-ACCEPTANCE (M8-07). The agent generates `docs/ACCEPTANCE.md` (M0-15: `node scripts/agent/acceptance.mjs`, from each ready feature's acceptance line and its entry in `docs/acceptance-plan.json`, which gives the place, the minutes, the exact steps and what a pass looks like; a unit test fails while the file is stale or the plan exceeds two hours) and opens one `needs-human` issue, _Galleon is ready for your acceptance session_, which reaches the owner as a GitHub notification e-mail.

**Who does what.** The owner holds the Nova and their phone and judges; the local Claude session on the Mac reads `docs/ACCEPTANCE.md`, explains each step in plain words, and does every terminal and GitHub step: SSH to the Nova, the read-only save backup, installing Galleon for real, approving the `release` environment on the owner's word, and pushing the results. Once Cut a release has published, the cloud agent opens a PR appending the run's job summary (release, commit, run) to `docs/PROGRESS.md` (M0-14).

**What is in it** (the generator orders it to need as few reboots as possible, at most two hours):

1. **Save backup first.** The local session copies the server's saves for the games the session will use, by GET only, to the Mac.
2. **Install v1.0.0 for real** (M8-01): `install.sh`, the Steam shortcut, the sign-in imported from RomMix. Galleon becomes the owner's launcher; stock RomMix stays installed and untouched.
3. **Look and feel** (M4-33): ten minutes through every screen.
4. **Buttons in the hand** (M7-12): each emulator's controls and holding Start to leave.
5. **Shader picks** (M7-13): two or three looks per system, pick one. Beside them, **4:3 and single-screen** (M7-17): one patched game per system fills the screen, and the DS and 3DS single-screen layout and its swap button. And **HD textures** (M7-23): one game with a pack per system shows them without loading stutter, the per-game switch turns them off, and the owner picks the per-system defaults.
6. **Gate 2** (M2-19): per system, Argosy on Android to Galleon on Linux and back.
7. **Decky panel** (M3-01), **start on boot** (M3-02, attended reboot), **installing a Steam game** (M5-04), **Jellyfin** (M6-09, skippable).
8. The informational items (for example sleeping mid-download), and re-confirming the per-system save choices (M2-08).

**Results.** The local session writes `acceptance/<date>/results.json` and pushes it to `device-results`:

```json
{
  "schema": 1,
  "date": "2026-12-01",
  "build": { "version": "1.0.0", "sha": "<40-hex commit>" },
  "items": [
    {
      "feature": "M4-33",
      "result": "pass",
      "notes": "readable at arm's length; prefers it to Steam"
    },
    {
      "feature": "M2-19",
      "system": "psp",
      "result": "fail",
      "notes": "conflict prompt on Android after the Linux save"
    }
  ],
  "choices": { "M7-13": { "snes": "crt-geom" }, "M2-08": { "ps1": "A" } }
}
```

Notes are in the owner's words, without addresses or account names. Each `fail` becomes a bug for the agent; when its fix passes its device checks, a short follow-up session repeats only that item.

**Reading them back.** `node scripts/agent/device-results.mjs --apply` reads every `acceptance/<date>/results.json` that no `ACCEPTANCE-RESULTS <date>` line in PROGRESS.md names, oldest first. An `acceptance` feature with an item marked `pass` and none marked `fail` passes (`PASSES <id> acceptance:<date>`); one with a failed item goes back to false; a `skip` decides nothing. Every failed item, informational ones included, opens one `[acceptance] <id> [<system>]` issue (labels `bug`, `acceptance`) unless one is open, quoting the notes as data. A file not in the shape above decides nothing and stays new until it is fixed. A later session decides over an earlier one.
